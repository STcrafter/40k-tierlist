# Big Mek Dakkarig: способности не участвовали в расчёте

Отчёт о работе от 2026-10-09.

## Задача

Способности в проекте реализованы и отображаются на сайте, но не влияют на
боевой расчёт. Разбирали на примере Big Mek Dakkarig (`78a7-cf35-aa8d-c420`):

- `Sustained Hits 1` при Riled Up;
- `Blitzkannon`: `+6 атак` против целей, не имеющих кейвордов `MONSTER`/`VEHICLE`.

Обе способности были описаны в ручном слое, обе ничего не давали в бою. Причина
оказалась разной.

## Причина 1: поле ауры, которое никто не читал

`LeaderAura.sustainedHits` было объявлено с комментарием «Riled Up» и заполнено в
четырёх записях — Big Mek, Dakkarig, Big Mek in Mega Armour, Big Mek with Shokk
Attack Gun. Но `applyAuraToWeapon` собирал кейворды оружия только из
`aura.weaponKeywords` и `aura.unitWeaponKeywords`. Значение `sustainedHits`
терялось.

Тест целостности ручного слоя этого не ловил: он проверяет поля верхнего уровня
`ManualAbility`, а `aura` проходит целиком, то есть насквозь просматривать его
было некому.

## Причина 2: кейворд, которого нет в движке

Бонус атак был записан строкой:

```
weaponKeywordsOn: [{ weapon: 'blitzkannon', keywords: ['+6 Atts vs non-MONSTER/VEHICLE'] }]
```

`parseKeyword` на незнакомом тексте не падает, а склеивает его в имя вида
`+6-atts-vs-non-monster/vehicle` и отдаёт дальше. Ни одно правило в `rules.ts` и
`simulate.ts` это имя не читает — бонус молча ничего не делал.

Была и вторая ошибка в той же строке: условие на цель разбирается только после
двоеточия (`parseCondition`), а в строке стоял союз «vs».

Проверка «каждый кейворд ручного слоя известен движку» это пропустила, потому что
`keywordStrings` собирал строки только из четырёх полей и не включал
`weaponKeywordsOn`.

## Решения

**Бонус по условию на цель выражен кейвордом, а не новым полем.** Условие «у цели
нет таких-то кейвордов» известно только в момент броска, в `rules.ts`, и уже
умеет выражаться через `KeywordCondition`. Если бы правило внесло +6 прямо в
`weapon.attacks`, бонус раздался бы по любой цели — а способность продолжала бы
выглядеть верно, то есть тир уехал бы молча.

**Имя `conditional-attacks` отделено от `extra-attacks` намеренно.** В 40k
`Extra Attacks` — другое правило («ещё одна атака этим рукопашным оружием»), и
`simulate.ts` делит по нему рукопашное оружие на основное и дополнительное.
Переиспользование имени сломало бы либо это разбиение, либо потребовало бы
различать оружие по имени правила.

## Изменения

| Файл | Что сделано |
| --- | --- |
| `src/combat/keywords.ts` | каноническое имя `conditional-attacks`; `dedupeKey` учитывает условие |
| `src/combat/rules.ts` | хук в `extraAttackDice`: `+N` атак при выполненном условии |
| `src/manual/abilities.ts` | `applyAuraToWeapon` читает `sustainedHits`; ауры разобраны таблицей; запись Dakkarig переведена на канонический кейворд |
| `src/manual/abilities.test.ts` | `keywordStrings` покрывает все поля со списками кейвордов; две проверки целостности ауры |
| `src/combat/simulate.test.ts` | обе стороны условия; два условных бонуса не схлопываются |
| `src/combat/adapter.test.ts` | Dakkarig получает Sustained Hits на всём оружии и `conditional-attacks` только на Blitzkannon |

### Побочная правка: `dedupeKey`

Ключ дедупликации кейвордов учитывает условие, а не только имя и цель. Раньше два
одноимённых кейворда с разными условиями схлопывались в один, то есть часть
условия терялась.

Это правка общего разбора кейвордов, а не только орков: она затрагивает любое
оружие, у которого есть два одноимённых кейворда с разными условиями. На
поведение существующих юнитов не повлияла — все тесты зелёные.

### Ауры переведены на таблицу

По просьбе владельца проекта. Раньше поля ауры разбирались руками, и именно
поэтому `sustainedHits` можно было объявить и забыть прочитать.

- `AURA_WEAPON_EFFECT_FIELDS` + исчерпывающая `AURA_WEAPON_EFFECTS` — по образцу
  `WEAPON_EFFECTS`. `applyAuraToWeapon` гоняет оружие по цепочке; эффекты
  возвращают оружие по ссылке, если поле не задано (лишняя аллокация на каждое
  оружие каждой модели каждого отряда).
- `AURA_NON_WEAPON_FIELDS` — поля моделей и utility-метки: `fnp`,
  `saveAtLeast`, `invulnAtLeast`, `stealth`, `meleeApWorsening`, `wardAura`.
- `_AuraFieldsAccountedFor` — проверка компиляцией: остаток `Exclude` обязан
  сойтись к `never`. Проверено пробой: временно добавленное поле дало
  `error TS2344: Type '"__probeNotHandled"' does not satisfy the constraint 'never'`.
  Проба убрана.

Побочный выигрыш: новое поле ауры теперь нельзя объявить и забыть — упадёт
компилятор. Цена: добавление поля требует выбора таблицы. Это осознанно, потому
что смешение «аура про оружие» и «аура про модели» и породило баг.

Тип `_AuraFieldsAccountedFor` экспортируется только потому, что включён
`noUnusedLocals`: иначе объявление «никем не используемое» само стало бы ошибкой
сборки. Смысла в нём никакого — важен лишь факт, что он компилируется.

## Проверка

- `npm run typecheck` — чисто;
- `npm test` — 457 тестов в 18 файлах;
- `npm run build` — собирается.

Тесты, которые закрывают именно эти баги:

- обе стороны условия: +6 атак против пехоты и 0 против `VEHICLE`;
- два `Conditional Attacks` с разными условиями не схлопываются;
- Dakkarig получает `Sustained Hits 1` на всём оружии;
- `conditional-attacks` достаётся только Blitzkannon, а не всему стрелковому;
- условие хранится как `negate`, а не списком целей.

## Уборка репозитория

- Удалён `scripts/tmp-probe-fnp.ts` — одноразовый диагностический скрипт по FNP,
  не вызывается ниоткуда и не прописан в `package.json`. Вопрос, который он
  диагностировал (условный FNP у Arco-Flagellants и Penitent Engines), закрыт
  записями `fnp: { value: 5 }` в ручном слое.
- Рабочее дерево было «грязным» на ~104 файлах без единого изменения байтов:
  в `.gitmodules` и прочих файлах `git status` показывал `M`, потому что
  `core.autocrlf=true` на Windows переписывает рабочую копию в CRLF, а
  нормализованное содержимое совпадает с `HEAD`. Убрано индексацией: закоммичено
  только шесть файлов с реальными правками.

`.gitattributes` в репозитории нет. Пока его нет, эта шумная картина будет
возвращаться у каждого на Windows. Лечится одной строкой
`* text=auto eol=lf` — но это политика всего репозитория, и решение о ней нужно
принимать отдельно, а не попутно с фиксом.

## Что осталось за рамками

Общий класс «поле объявлено, заполнено и молча не прочитано» закрыт для
`ManualAbility` и `LeaderAura`. Открытым остаётся `withLeader`
(`LeaderConditional`): у него нет ни таблицы, ни проверки целостности. Сейчас в
слое используются все пять его полей, поэтому проблема не проявилась, но
добавление шестого даст ту же молчаливую потерю.
